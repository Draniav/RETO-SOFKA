Arquitectura del reto técnico de automatización

Cómo están construidos los proyectos de automatización web, de API y de performance. Para cada uno: qué hace, cómo fluye una ejecución, qué responsabilidad tiene cada capa y qué contiene cada carpeta y archivo.

Visión general

La carpeta reto-tecnico-sofka agrupa tres proyectos independientes. Cada uno se ejecuta por separado, tiene sus propias dependencias y genera su propio reporte. No comparten código porque prueban sistemas distintos con herramientas distintas.

1 · Automatización web con Serenity BDD 01-automatizacion-web-serenity

En una frase: un archivo en lenguaje de negocio (Gherkin, en español) describe la compra. Cucumber conecta cada frase con código Java. Ese código usa el patrón Screenplay: un actor (“Cliente”) que tiene la habilidad de navegar ejecuta tareas sobre la página y hace preguntas para validar el resultado. Serenity coordina todo, toma capturas en cada paso y genera el reporte.

Cómo funciona una ejecución

El escenario que se ejecuta

Antecedentes: Dado que "Cliente" está en la tienda OpenCart Cuando agrega al carrito los productos | iPhone | MacBook | Y visualiza el carrito de compras Entonces debe ver en el carrito los productos | iPhone | MacBook | Cuando finaliza la compra como invitado con los datos (nombre, apellido, teléfono, dirección, ciudad, código postal, país, región) Entonces debe ver el mensaje de confirmación "Your order has been placed!"

Arquitectura por capas (patrón Screenplay)

Screenplay reparte el código según la pregunta que responde. Las capas de arriba hablan el idioma del negocio y las de abajo el del navegador. Si cambia un selector, solo se toca userinterfaces. Si cambia el proceso de compra, solo se tocan las tasks.

Feature¿Qué se quiere probar? Escenario en lenguaje de negocio y datos de prueba en tablas. · features/compra_como_invitado.feature
Step definitionsTraducen cada frase Gherkin a una llamada al actor. No contienen lógica de UI. · CompraComoInvitadoStepDefinitions, Hooks, TiposDeDatos
Tasks¿Qué hace el usuario? Acciones de negocio compuestas por interacciones. · AbrirLaTienda, AgregarAlCarrito, VerElCarrito, IniciarCheckoutComoInvitado, DiligenciarDatosDeFacturacion, ConfirmarElPedido, FinalizarLaCompraComoInvitado
Interactions¿Cómo lo hace? Acciones atómicas sobre un elemento. Serenity ya trae Click, Enter y SelectFromOptions; se agregó ClicCuandoSeaClicable (esperar y luego hacer clic).
Questions¿Qué ve el usuario? Leen el estado de la página para validarlo. · ProductosEnElCarrito, MensajeDeConfirmacion
User interfaces¿Dónde está cada cosa? Localizadores (Target) con nombre legible, agrupados por página. · PaginaInicio, PaginaResultadosBusqueda, PaginaProducto, PaginaCarrito, PaginaCheckout, PaginaPedidoConfirmado
Models y utilsSoporte: el objeto Comprador (inmutable, con Builder), GeneradorDeCorreo (correo único por ejecución) y EsperaMaxima (tiempos de espera centralizados).

2 · Automatización de API con Karate 02-automatizacion-api-karate

En una frase: Karate es un DSL que mezcla Gherkin con peticiones HTTP y aserciones JSON en el mismo archivo, sin escribir código Java para cada paso. Un runner de JUnit 5 ejecuta los .feature en paralelo. Cada escenario crea su propio usuario con datos únicos, prueba una operación y lo elimina al terminar.

Cómo funciona una ejecución

Qué prueba cada escenario

TagEscenarioPrecondiciónPetición y validaciones
@crearCrear un usuario—POST /user → 200, esquema de respuesta, message = id del usuario
@consultarBuscar el usuario creadocrear-usuarioGET /user/{username} → 200, esquema de usuario, cuerpo idéntico al enviado
@actualizarActualizar nombre y correocrear-usuarioPUT /user/{username} → 200, message = id
@consultar_actualizadoBuscar el usuario actualizadocrear + actualizarGET → nombre y correo nuevos, apellido sin cambios
@eliminarEliminar el usuariocrear-usuarioDELETE → 200, message = username; luego GET → 404 “User not found”
@e2eCiclo de vida completo—Los 5 pasos anteriores en orden, en un solo escenario

Ciclo de vida de un escenario

El ejemplo es “Buscar el usuario actualizado”. Los reintentos (retry until) existen porque la PetStore pública tiene varias réplicas: justo después de escribir, una consulta puede caer en una réplica que todavía no tiene el cambio.

Como cada escenario usa un username distinto y limpia sus datos, los escenarios no dependen entre sí. Por eso el runner los puede ejecutar en paralelo y en cualquier orden.

3 · Prueba de performance con k6 03-performance-k6

En una frase: k6 lanza usuarios virtuales que llaman al login de FakeStore a un ritmo fijo de peticiones por segundo. Cada petición usa credenciales del CSV y se valida con checks. Al final, los thresholds deciden si la prueba cumple los criterios (al menos 20 TPS, respuestas de hasta 1,5 s y menos de 3 % de errores) y se generan los reportes.

Cómo funciona una ejecución

Módulos del script

Arquetipo de carpetas y archivos

Cómo ejecutar

Requisitos: JDK 11 o superior, Google Chrome y k6. No hace falta instalar Gradle porque los proyectos Java incluyen el wrapper. Los comandos son para Windows; en Linux o macOS use ./gradlew.

Web · Serenity

cd 01-automatizacion-web-serenity gradlew.bat clean test gradlew.bat clean test -Dheadless.mode=true

Reporte: target/site/serenity/index.html

API · Karate

cd 02-automatizacion-api-karate gradlew.bat clean test gradlew.bat clean test "-Dkarate.options=--tags @e2e"

Reporte: build/karate-reports/karate-summary.html

Performance · k6

cd 03-performance-k6\ejercicio-1-carga-login k6 run src/login-load-test.js k6 run -e TPS_OBJETIVO=30 -e DURACION_SOSTENIDA=5m src/login-load-test.js

Reportes en reports/. Si algún criterio no se cumple, k6 termina con un código de salida distinto de 0, lo que sirve como compuerta en un pipeline de CI.
